# Parser recovery diagnostics: legacy / `_At` pairing inventory

Generated by Stage 1.3 of the Razor parser error-recovery redesign plan
(see `src/Razor/docs/plans/ErrorRecovery/razor-recovery-redesign-plan.md`).

For every legacy diagnostic factory in `RazorDiagnosticFactory.cs` whose
source span is authored as "from start of construct to current cursor"
(or otherwise wider than the missing-token cursor position) **and** which
is called from a recovery context in `CSharpCodeParser.cs`,
`HtmlMarkupParser.cs`, or `TokenizerBackedParser.cs`, Stage 1.3 added a
paired factory with suffix `_At` that takes a `SourceLocation` and emits
a zero-width `SourceSpan` at that location. The paired factory reuses
the legacy factory's `RazorDiagnosticDescriptor` (same `RZxxxx` ID, same
message) -- the only difference is the span width and starting
position.

The legacy factories are intentionally NOT removed; legacy code paths
still call them. Migration of call sites to the `_At` variants happens
in Stages 2.x / 3.x under the `UseEnhancedRecovery` feature flag.

## Out of scope for Stage 1.3

The following parsing factories were audited but **not** paired:

* Factories whose legacy span is already at (or very near) the
  missing-token cursor position. Adding an `_At` variant would be
  redundant. Examples: `Parsing_UnexpectedWhiteSpaceAtStartOfCodeBlock`,
  `Parsing_UnexpectedEndOfFileAtStartOfCodeBlock`,
  `Parsing_UnexpectedCharacterAtStartOfCodeBlock`,
  `Parsing_AtInCodeMustBeFollowedByColonParenOrIdentifierStart`,
  `Parsing_UnexpectedNestedCodeBlock`,
  `Parsing_InlineMarkupBlocksCannotBeNested`,
  `Parsing_DirectiveTokensMustBeSeparatedByWhitespace`,
  `Parsing_UnexpectedEOFAfterDirective`,
  `Parsing_SingleLineControlFlowStatementsCannotContainMarkup`,
  `Parsing_ReservedWord`,
  `Parsing_MarkupBlockMustStartWithTag`,
  `Parsing_TextTagCannotContainAttributes`.
* Factories whose span is intentionally wide to cover an invalid
  *value* the user provided (no missing token; the diagnostic is "what
  you wrote is bad"). Adding an `_At` variant would change the
  diagnostic's meaning. Examples: `Parsing_DuplicateDirective`,
  `Parsing_IncompleteQuotesAroundDirective`,
  `Parsing_InvalidTagHelperLookupText`,
  `Parsing_InvalidTagHelperPrefixValue`,
  `Parsing_HelperDirectiveNotAvailable`.
* Factories where the legacy span is over a found-but-unexpected
  current token (which is approximately at the missing-token site, just
  with a non-zero width). These are recovery sites and a future stage
  may opt to add `_At` variants if precise zero-width diagnostics are
  desired. Examples: `Parsing_DirectiveExpectsTypeName`,
  `Parsing_DirectiveExpectsNamespace`,
  `Parsing_DirectiveExpectsIdentifier`,
  `Parsing_DirectiveExpectsQuotedStringLiteral`,
  `Parsing_DirectiveExpectsBooleanLiteral`,
  `Parsing_DirectiveExpectsCSharpAttribute`,
  `Parsing_DirectiveExpectsIdentifierOrExpression`,
  `Parsing_GenericTypeParameterIdentifierMismatch`,
  `Parsing_UnexpectedIdentifier`,
  `Parsing_UnexpectedDirectiveLiteral`,
  `Parsing_DirectiveMustAppearAtStartOfLine`.

Per the plan's escalation rule, **adding an `_At` paired factory is
always safe** -- if a future stage discovers that one of the above
factories warrants a paired `_At` variant, it can be added at that
point without disturbing legacy call sites.
